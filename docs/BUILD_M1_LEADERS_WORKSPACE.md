# Milestone M1: Leaders workspace (admin)

Branch: `feature/m1-leaders-workspace`, created from the branch containing this file. Read `docs/BUILD_BRIEF.md` first; every rule there applies. Line numbers below are approximate anchors in the current files; search for the quoted code.

Goal: the page `/admin/leader-registry` becomes a professional, phone-first office tool: approve positions, add a leader with a photo in four easy steps, see the organisation chart, edit a leader's public profile, and end, transfer or archive. Nothing here changes the database; if you find a database change is needed, write it up under "NEEDS DB" in `docs/HANDOFF.md` and in the pull request (see the brief, section 3).

Steps (step indicator, Back button, all entered data kept when going back or when an error occurs; the form submits only on step 4):

4. Gusubiramo: summary list and one large Save button.

Then read back with `GET /api/admin/leader-registry/appointments?administrative_unit_id=<id>` and confirm the returned `appointment_id` is in the list; only then show "Byabitswe" with the short reference. If the server answers success but the read-back does not contain it, say so honestly. If the request fails ambiguously (network error, timeout, unreadable response) mark the attempt ambiguous: before any retry fetch the list for the same place and use `findAlreadySaved(...)`; if it finds the record, treat it as saved and never post again. After success show a success panel with "Andika undi" and "Funga".
Acceptance: works with keyboard and at 360 px; each validation message is next to its field; no duplicate record can be created by double-tap or retry.

## Task 4: organisation chart tab "Imiterere y'ubuyobozi"
Create `src/app/admin/leader-registry/OrgChart.tsx`. In `page.tsx` add `"orgchart"` to `type ActiveTab`, add a nav button next to the existing ones (around lines 630-645) and render the component for that tab.
- Lazy tree rooted at the admin's unit (`activeAssignment.boundary`). Expanding a node loads only its direct children from `/api/administrative-units` (province without `parent_id`, others with it; limit and pagination if more than 100). Never load a whole level of the country.
- Each node shows its current leaders (use `GET /api/admin/leader-registry/appointments?administrative_unit_id=<id>`): Avatar, name, position title, status chip (Ntiyemejwe / Itegereje gusuzumwa / Yemejwe / Yarangije). For every approved position whose required level equals the node's level and that has no active holder show a row "Umwanya urimo ubusa" with an "Andika" button that opens the wizard with place and position prefilled (add optional `initialPositionId` and `initialPlacePath` props to the wizard).
- Coverage counts such as "12 kuri 30 uturere dufite Meya": add a read-only route `src/app/api/admin/leader-registry/coverage/route.ts` that, for one parent unit and one position, returns the number of child units and the number with an active holder using two bounded queries (children ids, then `leader_appointments` filtered with `.in("administrative_unit_id", ids)` and the active statuses). Use `requireLeaderAdmin`, validate the query with zod, scope-check against the admin's assignment, no cross-scope data.
Acceptance: expanding any node answers in under 2 seconds on the real data size (explain your queries in the pull request); no request ever returns more than 200 units.
